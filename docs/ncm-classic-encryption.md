# CLASSIC_NCM 加密流程

## 适用范围

本文记录当前项目样本所使用的经典 NCM 容器加密方式，内部分类名称为 `CLASSIC_NCM`。

截至 2026-08-05，`example` 目录中的 7 个样本均符合该结构。文件日期和文件名不能用来判断版本，应当以容器头、密钥区、元数据区和音频解密结果为准。

## 容器组成

一个经典 NCM 文件依次包含以下内容：

1. 8 字节固定标识 `CTENFDAM`。
2. 2 字节格式标记。当前样本均为十六进制 `01 70`，但尚无证据证明它是正式版本号。
3. 4 字节小端序密钥区长度。
4. 指定长度的加密密钥区。
5. 4 字节小端序元数据区长度。
6. 指定长度的加密元数据区。
7. 4 字节 CRC 数据。
8. 5 字节保留区域。
9. 4 字节小端序封面长度。
10. 指定长度的封面原始数据。
11. 加密后的音频数据，直至文件结尾。

## 音频密钥的封装

音频数据使用一段音频流密钥处理。该密钥在写入 NCM 文件前，先在前面加上 ASCII 文本 `neteasecloudmusic`，然后使用 AES-128-ECB 和 PKCS5/PKCS7 填充方式加密。

AES 固定密钥的 ASCII 内容为：

```text
hzHRAmso5kInbaxW
```

AES 加密完成后，每个密文字节再与 `0x64` 做一次异或，结果作为文件中的密钥区。

完整方向如下：

```text
"neteasecloudmusic" + 音频流密钥
    -> AES-128-ECB-PKCS5Padding 加密
    -> 每字节 XOR 0x64
    -> 写入密钥区
```

## 元数据的封装

元数据是 UTF-8 JSON，包含歌曲 ID、歌曲名、歌手、专辑、码率、时长、音频格式等字段。

加密前先在 JSON 前加上 ASCII 文本 `music:`，然后使用另一组固定密钥执行 AES-128-ECB 和 PKCS5/PKCS7 填充加密。

元数据 AES 固定密钥的 ASCII 内容为：

```text
#14ljk_!\]&0U<'(
```

AES 密文经过 Base64 编码后，在前面加上 ASCII 文本 `163 key(Don't modify):`。最后，每个字节与 `0x63` 异或，结果写入元数据区。

完整方向如下：

```text
"music:" + UTF-8 JSON
    -> AES-128-ECB-PKCS5Padding 加密
    -> Base64 编码
    -> 添加 "163 key(Don't modify):" 前缀
    -> 每字节 XOR 0x63
    -> 写入元数据区
```

## 音频数据的处理

音频主体使用一种 RC4-like 算法处理，但它不是标准 RC4。算法先根据音频流密钥生成一个包含 0 到 255 的 S-box。

初始化时，令 `S[i] = i`，然后依次计算：

```text
j = (j + S[i] + key[i % keyLength]) % 256
交换 S[i] 和 S[j]
```

对于从 0 开始计数的音频绝对位置 `p`，生成一个密钥流字节：

```text
i = (p + 1) % 256
j = (S[i] + i) % 256
K = S[(S[i] + S[j]) % 256]
```

音频明文与 `K` 异或，得到写入 NCM 的密文：

```text
密文[p] = 明文[p] XOR K
```

这个阶段不会继续交换 S-box，因此密钥流以 256 字节为周期重复。加密和解密使用完全相同的异或操作。

## 封面和歌词

封面图片不经过上述音频加密，而是按长度直接保存在封面区。当前样本包含 JPEG 或 PNG 图片。

当前 7 个样本的元数据均不包含 `lrc`、`lyric` 或其他歌词字段。歌词不是这个经典 NCM 容器的已验证组成部分。
